AgentScore Roadmap

Beta onboarding, quality gate and self-improvement

Last updated 11-11-2026 · Horizons: Now / Next / Later

Target persona

A semi-technical user who can create agents but does not know how to configure traces, instrumentation, or agent updates. They create or evaluate agents and make the final call before an agent ships to production.

North star

Get as many users, including internal users, as possible using AgentScore regularly. The product must prove its value: users must actually use it and benefit from it. Onboarding should be so straightforward that the next action is never in question, and the user reaches a score they can act on as quickly as possible.

Target user flow

Steps 2 to 5 are Now, including the quality gate (step 4). Step 1 (Trident sign-in), steps 6 to 9 and step 10 (CI go / no-go) are Next, and steps 6 to 9 repeat until the score meets the ship bar. Steps 11 and 12 are Later. Internal coverage of Tricentis agents is Now and is not a numbered step. App usability, the JEV / decision model, and session grouping are Next and are not numbered steps. The previous self-improvement loop is marked done and is not on this diagram. Steps 4 and 10 are new on 11-11.

Now

Improved onboarding

The first session, from sign-in to a first score, where every screen has one next action. Steps 2 and 3. First login with no data goes straight to the MCP connection step, a waiting screen holds until auth completes, and the user is guided to the first score and advice.

Why it matters

The persona can create agents and does not know how to configure traces. A screen with several ways forward loses them before the first score. Self-service onboarding is a High ask from Wolters Kluwer and L'Oreal. Labs graduation criterion 1 is real active use, which depends on people reaching a score quickly. The 11-11 sync made the HTML mock the base for the engineer's spec. Still open: verdict names differ by screen.

Goal: a user always knows the single next action, and reaches one score and one verdict for an agent they already run.
  • Guided first session Steps 2, 3
    Connect on first login, a waiting screen until MCP auth completes, progress to about 20 traces, then the score, an Improve button and plain-language advice, in the web app and in the coding agent's thread. No trace setup, profile picking, or eval writing on this path.

Quality gate

Each agent gets one gate (open, closed, or not enough data) from conditions the customer chooses over scored traces. Failing traces are flagged. Signal only: it never blocks a deploy and never changes the verdict. Step 4. New on 11-11.

Why it matters

The verdict is a weighted average, so one trace that leaks personal data barely moves it. Georgie Zaguirre asked for a security gate after ATA read 88% ready to ship while completing tasks correctly about 40% of the time (Internal Feedback Log, High). Tritusa asked for safety findings and company guardrails on 11-10 (compliance row, High, x2). The CI/CD gate row (High, Eaton and Accenture) is the strongest demand for a pass / fail. The brief is approved and coding starts after product review.

Goal: a user can say "this must never fail" about a check and get a clear open or closed answer that names the failing condition and links to the traces.
  • Gate conditions and gate state Step 4
    Share of flagged traces (with an "any single trace" preset), a floor on an eval, dimension or overall score, and a drop from the previous revision. Merges the internal security gate ask.
    AI-17189Brief only: no epic or build stories
  • Flags, acknowledge and override
    A flagged trace shows the condition, score and judge's reason, and trace lists filter to flags. Acknowledge a false alarm, or override a closed gate, with a required reason.
    AI-17189
  • Tenant-level conditions and templates
    Mandatory tenant conditions from the back office. Shipped privacy, security and safety templates. Authoring in a form or through the chat assistant behind the approval card.
    AI-17189
  • Gate history and read surfaces
    Every change recorded with its evidence. Readable in the app, back office, customer app API, MCP and the AI Workspace internal API. Adds "start a revision" to the customer app.
    AI-17189
Dispute risk: v1 has no CI API and no native CI integration, so Eaton's and Accenture's "block the release in CI" is not met here. Georgie's "cannot be marked ready to ship" is not met either: the gate stays separate from the verdict, as the brief decides.

Workflow management

A multi-agent flow is shown as one workflow. Step 5.

Why it matters

Evaluating a group or hierarchy of agents is a High ask from Meta, Wolters Kluwer, Aptiv, Eaton, and Accenture. Aptiv asked to store and score a workflow as a whole. Accenture marked multi-agent workflow testing as priority 1. This theme is the showing and grouping.

Goal: a user who runs several agents together sees that flow as one workflow.
  • Workflow-level grouping Step 5
    Multi-agent flows are grouped and shown as one workflow.

Internal Tricentis agents

Every internal Tricentis agent is scored in AgentScore. An adoption outcome. It should not require AgentScore product work.

Why it matters

The north star is regular use, including by internal users. A full internal footprint is the proof that AgentScore is where Tricentis scores its own agents. It is on Now because it matters now and it does not wait on a product change.

Goal: internal Tricentis agents are connected and scoring, without a new AgentScore feature.

Stimulation testing

AgentScore profiles an agent, generates targeted tests from its traces and evals, has them run, and scores the results, so a user can test without waiting for organic traces. Steps 6 to 10. On 11-11 the sync decided the user's coding agent pulls the suite through the MCP and runs it, with a CLI as the optional happy path.

Why it matters

Scenario bank and simulation testing is the top High ask across Meta (x2), L'Oreal, Tritusa, Eaton, PG&E, and Accenture, and the pivotal gap for the Meta POC. On 11-10 Tritusa asked for safety findings: organic traces cannot show an agent will never leak PII, so it has to be prompted with test inputs. The differentiator is the knowledge base of failure modes by agent type, not the test mechanics.

Goal: an agent is profiled, given the test categories that fit it, tested by the user's coding agent, and scored, with improvements and a go / no-go a pipeline can read.

JEV / decision model

A hybrid scorer. JEV runs where it applies. The fuller judge runs where it does not. The point is less scoring time and less scoring cost.

Why it matters

Scoring cost and latency cap how often a user can run, and how many agents a tenant can keep on a score. A cheaper model on the cases it can decide keeps the fuller judge for the cases that need it.

Goal: each eval uses the cheaper model when that model is fit for the check, and the judge when it is not.
  • Hybrid JEV and judge
    Use JEV where it applies, and the current judge where it does not, to save scoring time and cost.
    No Jira found
Dispute risk: what JEV expands to is unconfirmed. This card treats it as a cheaper decision model beside the current judge.

Session grouping

Related traces from one agent are grouped into a task or conversation, and the score covers that whole session. The per-agent scorecard is marked done.

Why it matters

A score on one trace misses a multi-step task. The August 24 working session called session-based scoring one of the two highest-priority product gaps. Workflow-level grouping is Now and is a different cut.

Goal: a user can score a whole task or conversation, not only a single trace.
