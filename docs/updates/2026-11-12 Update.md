## Key Discussion Points
1. Tricentis Identity (Trident)
   - Tim found the Trident information chaotic. Customers will also migrate one at a time, so dev work could land before the customer who needs it has migrated.
   - Lior suggested using it first for the internal back office (replacing the Microsoft login) while customers stay on the Tosca-level login. He said a swap would take two to three days, and the system can run both side by side.
   - Agreed: do it when Trident is ready, not before.
2. Onboarding update
   - Andrew sent out the updated onboarding solution and wants feedback. Tim offered to walk through it.
   - Lior said the onboarding depends on two features:
     - MCP connection monitoring: detects traffic on the MCP layer and records it, so onboarding can confirm "you're connected". This is complete and about to be released.
     - Agent display name: a friendly name, separate from `service.name` / `agent.name`. Agents cannot be renamed today. Lior is building it as a full feature: the display name is attached to traces, shown in the back office, the customer app, and the MCP, and is searchable. He expects to finish it within a few hours.
   - Once both features are in, Lior will build the onboarding across all surfaces and expects to finish by the end of Friday.
3. Internal agents
   - Many more internal agents are coming in. The person transcribed as "drawer" / "George" has 30+ internal agents to score.
   - For now these agents will conform to what AgentScore needs. Session-based or task-based scoring will be looked at later. The goal is fast feedback.
4. Quality gates
   - Andrew's target experience: the user connects an agent, AgentScore collects 20 traces and identifies the agent type (for example a customer service bot, so test for PII), the user sets a threshold, and AgentScore raises a security-violation flag on offending traces.
   - Lior's plan matches this: flags on traces, user-defined gate rules (for example "close the gate if PII is flagged in the last 10 traces"), the flag shown in the UI, and gate status plus the reason returned to coding agents through the MCP.
   - Andrew approved Lior to start.
5. Plain-language evals and simpler attribution
   - Lior said plain-language eval creation already exists in three places: the MCP and coding agent, the assistant in the web app, and the web UI form. No new work needed.
   - Andrew mentioned simpler attribution as upcoming work, likely UI and prompt changes to how results are reported.
6. Insights for internal users
   - Andrew asked for insights to record the behavior of internal Tricentis users who are not admins (everyone except Andrew, Lior, and Tim), ahead of the internal influx. He will file a ticket.
   - Lior said it is a very small change.
7. External feedback outreach
   - External feedback has been slow. Andrew identified 49 signed-up accounts that match the ideal customer profile: not in a regulated industry, known to run agents, and open to innovation (or with small innovation-focused teams).
   - He is asking each Tricentis account owner to schedule an AgentScore introduction.
8. CLI
   - Lior is building a CLI alongside the MCP, so users can pick based on what they are able to run.
9. CI/CD experiment and positioning
   - Kareem and Roger have both asked for CI/CD.
   - Andrew sees a possible second market: AgentScore as the company-wide eval platform, with the same dataset and yardstick across teams that use LangSmith, Weights & Biases, and so on. Engineering features such as CI/CD and alerting support that positioning.
   - Tim will build it as an experiment. Then they will ask Kareem whether he would use it.
10. Agent platform integrations (SAP Joule first)
    - Several requests to integrate with agent-building platforms (Microsoft Copilot, Azure AI Foundry, and so on), including four for SAP Joule.
    - Andrew wants a proof of concept for SAP that shows how a customer with an agent in SAP would connect it and get traces into AgentScore. Then expand to Copilot, Foundry, Google, OpenAI, and others.
    - Differentiator: AWS AgentCore and similar tools score only their own agents. Nothing covers a mix of AWS, other platforms, and homegrown agents.
    - Lior thinks it may already work if the platforms emit OpenTelemetry, perhaps with tweaks for how tools and attributes appear in their traces. Agreed: it needs testing.
11. Simulation testing through the coding agent
    - Lior's proposal: AgentScore prepares simulation test cases from the agent's traces. The user's coding agent loads them through the MCP and decides how to inject them into the agent. The coding agent closes the loop, not AgentScore.
    - Tim agreed. AWS Strands Evals and AgentCore Evaluations also require in-process, code-level integration. A coding agent gives a universal way to do it, because it can choose whatever method fits the agent.
    - Two modes:
      - Local development: the coding agent pulls scenarios through the MCP and drives the agent under development.
      - CI: more scripted and deterministic, with no coding agent at run time. The coding agent's job is to set up how CI drives the agent under test.
    - Tim thinks it is solvable and can demo it.
    - Andrew asked how this works for a live production agent (for example a travel-site chatbot). Lior separated the lifecycle stages: today's focus is development and testing; production operations would need a separate interface or API. Scope for now: the agent under test in development.
12. Production alerting and telemetry export
    - Lior: an endpoint or signal saying "stop, something went wrong" in production (for example a sudden PII flag after someone changes the agent's instructions) could be a value proposition other eval tools lack.
    - Tim asked whether notifications should live inside AgentScore or be exported as telemetry to the customer's event monitoring. Andrew and Tim leaned toward export as easiest, since target customers likely already have monitoring.
    - Tim: if we export alerts, export all scores. Lior agreed, possibly per tenant.
    - Andrew's longer-term idea: a tenant-wide agent report with a quantitative cost function (tokens saved, failed tool calls reduced, GDPR violations prevented). This fits a "company platform for agents" direction.
13. Documentation refresh
    - Andrew will open a docs refresh PR later today and send it for review.

## Decisions Made
- Trident is deferred until it is ready. If adopted early, the internal back office would go first.
- Agent display name is a first-class field: attached to traces, shown everywhere, and searchable.
- Lior is approved to start on quality gates (trace flags, user gate rules, gate status through the MCP).
- Internal agents conform to AgentScore's current model for now. Session-based and task-based scoring come later.
- No new work on plain-language evals; the three existing paths cover it.
- Simulation testing: AgentScore prepares scenarios from traces, and the user's coding agent runs them through the MCP. Scope is the agent under test in development, not production.
- Alerting direction (leaning): export scores and alerts as telemetry to the customer's existing monitoring rather than build notifications into AgentScore.
