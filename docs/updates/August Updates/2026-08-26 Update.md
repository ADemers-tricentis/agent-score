## Team Updates

### Lior
Running five tracks in parallel:
1. **Ingest-service refactor.** Handling massive volume (millions of spans, ~99.9% discarded as junk). Fixed a poison trace this morning — a rogue trace with >5,000 spans too large to fit in memory, which caused a container OOM. Refactoring the whole ingestion route to detect/handle poison traces, cut the memory footprint, rely directly on S3 + Postgres (no Langfuse), and scale to ~10x more traffic. Today/tomorrow.
2. **LLM catalog.** Assign any task to any LLM (e.g., scoring on GPT, a specific model, or a cheaper model) for flexibility and cost savings. Also enables cost/usage reporting: the trace's own inference cost (what it cost the user to run it, unrelated to us) and the cost to score it (computed from LLM tokens consumed via a read/write token-price map + multiplier — measured on one real run, not predicted).
3. **Overall usage tracking** (as previously discussed).
4. **Dynamic profiling** — starting.
5. **Sessions.** Deployed part of it to test whether session IDs can be distinguished from traces. Finding: a session ID is present almost everywhere and is ~1:1 with traces (no session seen yet with more than one trace); a single trace already captures the full back-and-forth (observed a 21-minute trace). Implication: today trace ≈ session, so scoring 20 traces = scoring 20 sessions — bulk scoring may be unnecessary (perhaps score only the final one). Letting it run a couple more days before deciding; design will still allow a session to hold ≥1 trace and support manually combining traces if ever needed. Session IDs are set partly automatically by the OTel stack running the agents, so external users with their own OTel stack (logfire, Langfuse, etc.) already get automatic session IDs.
