## Key Discussion Points
1. Quality gate proposal
   - The engineer sent a ticket with the full proposal (design, how to build it, spec).
   - The product owner will read it, comment, and approve; coding starts after approval.
2. Engineer's upcoming prep work
   - On-prem readiness.
   - The ad hoc task idea (a user sends a one-time task to an agent and gets a score). The product owner likes the idea but is unsure how it would work and does not want users confused about which path to use to send work to their agent.
3. Guided onboarding flow (HTML mock)
   - First login with no data goes straight to the MCP connection step.
   - A waiting screen holds until the user authenticates via the MCP, then shows a completion message and moves on.
   - Then an in-progress state with a command the user can run to check, followed by a "we're scoring, now you can ask the agent" step, shown in Claude Code.
   - Goal: guide every step so the user always knows what to do next.
   - Possible later variant for users who prefer the UI over the MCP. Not enough data yet on UI vs MCP usage.
4. Safety findings and simulation testing
   - Tritusa (the only active users) asked for safety findings on a call last night. This feeds the safety gate.
   - Organic traces are not enough to be sure an agent will not leak PII or is GDPR compliant. The agent has to be prompted with test inputs.
   - Open problem: how to connect to the user's agent and run, for example, 50 prompts against it.
   - Proposed approach: generate a test suite from existing traces, expose it through the MCP, and let the user's coding agent pull it, decide how to run it (script or otherwise), inject it, and send traces back for scoring. This forms a loop, like writing unit tests and re-running them.
   - Tests and their results would be stored per agent and linked together. Existing evals (for example the PII eval) can drive adversarial test generation. The existing "improve" function is a model for a similar "test" action.
   - Concern raised: a user could do all of this with their own coding agent. Response: the differentiator is the knowledge base (common failure modes by agent type, what to test, why, and how to read results), not the mechanics of generating tests.
5. MCP app (visual UI inside the coding tool)
   - Idea: an MCP app panel (as in Cursor) with a button such as "run adversarial testing". The engineer questioned the need, since the customer website already provides a visual UI. Left open.
6. CI / CLI
   - Missing piece: CI integration. A CLI or MCP could run the simulation tests and return a go / no-go signal.
   - The CLI is currently a wrapper around the MCP with no extra business logic. Agreed to build it as the optional happy path, with the MCP-only route still working (less polished).
   - The engineer will talk to the teammate who worked on simulation and take the idea further.

## Decisions Made
- Onboarding: the HTML mock is the base for the engineer's spec; the ticket is a brief plus the HTML attached.
- Simulation testing: test suite exposed via the MCP, executed by the user's coding agent in a loop with trace feedback.
- Build a CLI as the optional happy path, with the MCP as fallback.
- Coding on the quality gate starts only after the product owner approves the proposal.
