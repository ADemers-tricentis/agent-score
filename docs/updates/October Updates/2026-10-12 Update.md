## Key Discussion Points
1. **AgentScore as the evaluator for coding agents (Claude, Cursor, etc.)**
   - Users increasingly have the coding agent write prompts and tools. Coding agents are bad at building benchmarks and defining "what good looks like," and the target market are not data scientists.
   - AgentScore should connect directly to the coding agent, tell it what to test (e.g. for a RAG chatbot: data poisoning, similar documents with different meanings), then score the run and return classes of errors.
   - Goal is recursive self-improvement (RSI): turnaround goes from weeks to minutes, repeated until accuracy climbs.
   - AgentScore must withhold enough to prevent benchmark hacking: return error classes, not answers.
   - This also solves the getting-started problem: "here's AgentScore, here's my API key, go set up the MCP." The coding agent adds OpenTelemetry etc. itself. Reference: WorkOS onboarding (prompt + MCP endpoint, identity set up in ~8 minutes). Same experience wanted for internal teams onboarding ATA, ATC, etc.

2. **Andrew's goals for the onboarding / two-way interface (PRD shared on screen)**
   - Target persona: non-technical or semi-technical AgentScore user (PM, solutions engineer, customer success) who may not know what OpenTelemetry is.
   - Nothing installed locally; AgentScore hosts it and Claude points at a URL. Existing skill (detects stack, adds instrumentation or exporter) is the proof of concept.
   - Flow: check the agent, plan instrumentation, apply it, verify it works, all before any traces are sent.
   - Unproven part: "get scoring suggestions" in plain language, optionally auto-applied.
   - Nice to have: MCP app with interactive UI (progress / status diagram).
   - Mechanism is open: Andrew does not care if it's MCP or something else, only about ease.

3. **Autonomy levels and recommendation design**
   - David: AgentScore does not set autonomy levels; the caller/end user does, per agent, in their own client. Andrew agreed.
   - Options to present: propose only (plain-language list + how-to instructions), apply low-risk changes, fully autonomous agent-to-agent.
   - Guardrail idea from Andrew: one change per cycle so score movement can be attributed.
   - David: how AgentScore phrases recommendations will drive what the other agent does (e.g. listing every problem invites a full prompt rewrite). Recommendations need to be judicious and heavily tested. This part is on us.

4. **MCP vs skill**
   - Tim: the earlier discussion (setup only, mainly API key handling) didn't justify an MCP over a skill. The repeated improvement workflow (fetch scores, fetch recommendations) does justify MCP.

5. **Market: semi-technical builders**
   - Andrew market-tested with friends (director of logistics, program manager) building agents in Claude with no idea if they work. Lowering barrier to building agents raises the need for easy evaluation (e.g. pinpointing regressions when a new model ships).
   - David: call them "semi-technical" - PMs, directors, people around product development who know the lingo. Fully non-technical business users likely aren't building agents in Claude yet (they stall at "initialize a Git repo").

6. **Stimulation project (greenfield)**
   - The other half: how to drive an agent's UI/API to generate load for evaluation, since not all agents are built in Claude/Cursor. David told Eran and Landsberg not to attach this to ATA, ADA, or Exploratory. Use any driver (e.g. Playwright); the depth is in what to tell the agent to do.
   - Tim: synthetic dev/test cases must stay grounded in real production usage. AgentScore already has production data to connect.
   - David: it's a Venn diagram, not a circle. Some scenarios should never appear in production (e.g. a 12-year-old asking for an insurance quote, secret shopper) - COPPA, EU AI Act violations. Two top-tier problems: grounding benchmarks in production (grades) and finding unanticipated risk gaps (gates, 0% tolerance, negative testing).
   - David corrected the term: "stimulation," not "simulation" - injecting inputs, not mocking results. Joked about "Project Caffeine."

7. **Buy vs build (Arato, name as transcribed)**
   - Andrew found several well-featured vendors, few open-source options.
   - David: Arato at ~$1M ARR would cost ~$10M; would need to show Arato + Tricentis is worth more than that, and buying likely means the team moves onto that platform. Counter-question: what's the cost to clean-room it from public info with a swarm of Claude agents? "We don't have to be better than them to beat them," just good enough in front of more people.

8. **Staffing and team shape**
   - David will add people only after Andrew shows the program scales to two engineers. Fast engineers with full autonomy over a contained domain beat teams; overlapping domains (e.g. prior AgentScore + TAIS team) caused cross-talk.
   - Tim prefers working solo early; what he lacks is context on infrastructure and internal acronyms, not teammates. Would decrease productivity with three more people right now.
   - Andrew lacks domain knowledge for the long tail of risk/regulatory scenarios (beyond GDPR, EU AI Act, HIPAA, PII). David: the ideal reviewer is an AI safety officer; probably not in Tricentis. Proposed a customer coalition of procurement/AI-governance people from customers.

9. **Software factory and regression testing**
   - David: well-formed Jira ticket -> agent creates branch, builds code, opens PR, posts evidence (screenshots, recordings) back to Jira; Andrew reviews via comments. No auto-merge; engineer reviews. Eldar (Israeli team) can help with connections.
   - Andrew asked to add regression testing because things are slipping. David: regression testing is mandatory before users see it; PM is the gate, QE manager, and requirement creator. Needs simulated environments/mocks so it doesn't burn tokens.
   - Human roles: PM judges whether the UX is right and filters conflicting feedback (Tim: one customer says blue, another red). Engineers judge whether solutions scale (agents pick the shortest path, e.g. caching a 10 MB document).
   - Current flow: Andrew makes customer-facing changes himself, Lior reviews and merges.

## Decisions Made
- Three work streams:
  1. **AgentScore <-> coding agent (RSI loop + zero-install onboarding):** Lior. He also takes the current-app feature backlog/comments since he has full app context.
  2. **Stimulation ("Project Caffeine"):** Tim. Covers production-grounded baselines (grades) and risk/regulatory gap scenarios (gates).
  3. **Operationalize / software factory:** Lior builds the factory; a dedicated, in-time-zone person (possibly Neil) operates it on feedback, targeting ~10-minute turnaround.
- Autonomy level is set by the end user per agent in their own client, not by AgentScore. AgentScore owns how recommendations are framed.
- Delivery mechanism (MCP or otherwise) is open; MCP is currently favored because of the two-way improvement loop.
- Regression testing is mandatory before broader user exposure.
- Stimulation work is not to be attached to ATA, ADA, or Exploratory.
- No team additions beyond the three streams for now; start onboarding the factory operator now, before feedback volume arrives.
