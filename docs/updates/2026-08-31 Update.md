## The big topic: how to evaluate *huge* traces (Lior's new approach)

### The problem Lior found

When AgentScore evaluates an agent's behavior, it feeds the agent's "trace" (the full log of a session — every step, tool call, and data handoff) to an LLM judge for grading. That works fine for small traces (~10–40K). But real agent sessions — lots of interactions, tools shuffling data around — can produce traces of **30–40 MB**. Those don't fit in the LLM judge's context window, so **they simply weren't being scored**. And when he researched competitors, nobody has a clean solution for grading traces this big.

### Lior's solution (the important part for you)

Borrow the pattern that coding agents (Cursor, Claude Code, Codex) use. Those tools don't stuff an entire codebase into the model. Instead the agent acts as an **orchestrator** with basic tools (read, find, search/grep), and it pulls only the specific slices of data it needs.

Applied to AgentScore: he built an **agent layer** that sits on top of the trace storage (Postgres + S3) with search tools. Instead of dumping a whole 40 MB trace into the judge, the agent surgically fetches only the relevant pieces the evaluation criteria call for.

**Why it matters (the numbers he tested):**

- On a 40 MB trace, the agent touched only **~0.2%** of the data to get what it needed.
- Cost: **~77 cents** per evaluation instead of a much larger bill (or outright failure).
- He ran the same trace 10 times: output varied by **<5%** — i.e., reasonably repeatable.

**Bonus upside:** this same agent layer becomes the foundation for other features — a **chat interface** to the system, **dynamic scoring/profiling**, and "how do I get my score from 65 to 80?" advisory agents. One thin, reusable layer.

**Marketing angle Lior flagged:** competitors handle big traces with awkward workarounds (slicing, summarizing, hierarchies) or force customers to build their own mechanism. AgentScore could offer "give us a 50 MB trace and watch" as a differentiator.

## The technical debate you should understand (determinism)

This is the one point of tension, raised by **Andrew** and echoed by **Sohil** — worth understanding because it's a real risk, not resolved.

- **Andrew's concern:** An agent *choosing* which tool to call is **probabilistic** — it might not do the same thing every time. When you have many agents coordinating, you lose control and predictability over *what gets evaluated when*. A deterministic layer is safer.
- **Lior's rebuttal:** The **"blueprint" is deterministic** — each score profile defines fixed dimensions and a fixed set of "evals" (each eval returns a clean yes/no). The agent isn't *deciding what to evaluate*; it's only orchestrating *how to fetch the data* for a predetermined checklist. Each eval runs in its own isolated context (no "context pollution"), so results stay consistent. He's reusing a proven sub-agent/graph pattern from a prior project ("AirWorks").
- **Andrew's honest caveat:** "An agent following a blueprint is *not* determinism" — it can drift depending on its context. He's fine with it **as long as Lior and Sohil demonstrate two things: quality holds up, and cost stays low** (his line: "not $100 per evaluation"). That's the acceptance bar.

**Sohil's side suggestion:** rather than building the search engine from scratch, consider an off-the-shelf **enterprise context engine** (Tab9 / "graphify core") — "why reinvent the wheel." Lior pushed back hard: those are built for static codebases, whereas AgentScore ingests **thousands of dynamic traces per minute** and sometimes needs to score across multiple traces at once. He's using **Strands** (the same SDK AgentScore's agent core already uses) so it drops in cleanly. Andrew's ruling: approach is right, tool choice is the team's call.

**Timeline:** Lior expects it **up and running in 2–3 days** to start tuning. He noted results depend heavily on which model powers the orchestrator — picking the right one is still an open tuning task.
