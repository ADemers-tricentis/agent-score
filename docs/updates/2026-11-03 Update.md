## Summary

The team worked through why internal Tricentis agents show up badly in AgentScore: a trace is many services, `service.name` does not equal the agent a person wants scored, and some agents (Quality Agent) never run as a single process. The working agreement is to meet the teams that own those agents, learn what they want measured, and hand them a short instrumentation guide rather than invent a new aggregation rule for every repo. Workflow-level scoring stayed open. For AI Workspace, Lior's view is that AgentScore should keep scoring each agent and let AI Workspace roll scores up, because it already knows the workflow graph. External customers are a separate case.

## Key Discussion Points

1. **How the service list is filled**
   - The services shown in AgentScore come from the trace, from a field like `service.name`. They are not a curated catalog of agents.
   - A long trace where the user has to scroll past unrelated spans is why Lior wants broad detection rules, tied to an attribute, rather than a rule per eval.
   - Better Stack lists agents that AgentScore does not, including the APT / Performance Agent. AI chat and the chatbot also fail to line up.

2. **A trace is not one service**
   - Tim's read from yesterday: deciding "the" service for a trace is messy, because a distributed trace is spans from many services on purpose. Treating a trace as one service cuts against how OpenTelemetry traces are meant to work.
   - Most observability use of traces never needs this. Agent evaluation on OpenTelemetry traces is the smaller slice. Transcript-style uploads are more common elsewhere: one complete interaction, already known to come from one agent, with prompts, tool calls, and replies inline. Traces still win on detail that never reaches a transcript, including tool-call parameters and back-and-forth that is not user-facing.

3. **Quality Agent does not run as one agent**
   - Quality Agent is split by design. What runs is pieces such as the coverage plan graph, called when needed. The chatbot agent graph (agent graph) calls those pieces, so the work is attributed to the caller.
   - On a large trace, only a few spans are the agent. Everything else is noise, and AgentScore needs a way to pull the agent spans out.
   - The APT / Performance Agent is missing in AgentScore because `service.name` is not set. Tim found the Performance Agent code in NeoLoad is not putting the expected attributes on all of its spans.

4. **Who adapts to whom**
   - Lior: stop bending AgentScore to each team's current spans. Tell them what to do. One attribute on the span (agent name, workflow name, or similar) is enough, and AgentScore adds that attribute to its detection rules. If they want 17 sub-agents scored separately, they say how to tell those traces apart. If they want one master agent, that is also fine. The missing input is what they want measured.
   - The host: Tricentis builds agents ad hoc, each a little differently, and other companies will have the same problem. A pure "you must conform" stance is hard to hold. Do both: publish the path that works, and keep a backup for agents that are a pile of tool calls.
   - Tim: in classic tracing this is not a bug. He has been tuning attributes in agent repos and has no short doc that says which labels AgentScore looks for, or how to roll 17 sub-agents into one agent versus split a chatbot rollup apart. He does not see dev teams waiting on that doc. The pressure to use AgentScore internally is coming from above, not from the teams.
   - The host, after Lior left: the leadership push is real (use AgentScore on Tricentis agents, prove it internally), and lower friction matters. Prefer telling teams "do X, Y, and Z" over waiting for each team to define the product. The MCP is available end to end and those teams should try it. The same instructions could live in the MCP docs.

5. **Internal agents leadership wants scored**
   - David Landsberg and David Caldwell are pushing hard to evaluate internal agents with AgentScore.
   - ATA is the one that attributes and scores as designed. The host's read is that this is because Tim did the instrumentation work for that autonomous service.
   - They want the same for the APT / Performance Agent, Quality Agent, the chatbot, and the separate Tricentis agent.
   - Akash has a personal eval repo for this. Lior met him in Austin and wants that repo used as the clue to what they are asking to see, and how he already separates the pieces.

6. **Scoring a whole workflow, not only each agent**
   - The host raised multi-agent workflows, in AI Workspace and at customers. Companies want the handoff, shared state, and the final approval or action scored, including when each agent did its own task well and the failure is between them. A few customers, including heavy AI Workspace users at Wolters Kluwer, have said they will not try AgentScore until workflow evaluation exists.
   - Tim: the workflow engine should set a root trace id at the start and propagate it into every step, so AgentScore scores one trace. He also thinks hand-built workflow engines that pass work from agent to agent are falling out of favor. The forward-looking shape is one agent, with tools, running as long as it needs.
   - Lior: AI Workspace already has a workflow id when a workflow starts, and it should be on the traces. If it is missing, it is a small pull request to the AI workers. He doubts one rolled-up trace is the right score. Each step is an agent and should be traced and scored on its own. AgentScore already has sessions that can hold many traces, so a workflow id can sit on the session. A possible new concept is a group of agents that already have scores and evals, with an aggregate score for the group and drill-down to the weak agent. His suggested way to learn is to take a couple of real AI Workspace workflows, list the agents and their scores, and see which rollup is meaningful.
   - The host: an aggregate of per-agent scores misses the handoff failure (wrong tool, bad context, malformed output) that sits between agent A and agent B. Lior's reply: that failure is visible in the trace once you know A and B are connected. The gap is the relationship, not the span data.
   - Lior on who should present it: AI Workspace already knows which agents belong to which workflow, and one agent can sit in two workflows. AI Workspace should call the AgentScore API, take scores and recommendations, aggregate them, and let the user act there. A Wolters Kluwer user should not bounce from AI Workspace to AgentScore and back to fix something. AgentScore stays the scoring provider. He treats external agents, which Tricentis does not control, as a different problem. The host left this open and wants to talk to more people.
   - Tim's worry, after Lior left: the team may be assuming that only Tricentis agents are "seven tools in a trench coat," and that outside customers have neat single-process agents. If many customers decompose agents the same way, the prescribed attributes will not be enough.

## Decisions Made

- Agent teams should mark spans with an agreed attribute (agent name, workflow name, or similar). AgentScore will detect agents from that attribute. The exact attribute is still to be agreed with each team.
- What gets scored is driven by what the owning team wants measured: separate sub-agents, or one master agent. AgentScore will not guess that split.
- For AI Workspace, Lior's direction (not fully closed by the host): score each agent, expose score, evaluation, and recommendations over the API, and let AI Workspace own workflow aggregation and the improvement UI. External, uncontrolled agents stay a separate design.
- Tricentis accounts stay hidden by default on the Insights tab.
- The restart trace-loss bug is already fixed. No further action.
