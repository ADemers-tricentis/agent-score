# Meeting Summary: AgentScore - Migration Update and Proposal Review

**Date:** August 24, 2026
**Attendees:** Andrew, Lior (engineering lead), plus two additional team members (speaker identities not confirmed from transcript - one working on the Postgres/S3 persistence layer and RDS testing, one briefly present)
**Type:** Project review / working session

## Purpose
Review the completed Langfuse-to-Postgres+S3 migration, walk through open questions on the AgentScore proposal (scorecards, sessions, dynamic scoring), and align on next steps for TAIS integration and internal agent onboarding.

## Key Discussion Points

### 1. Langfuse to Postgres/S3 Migration - Status
- Migration is complete and running in production. Lior described it as a heavy lift: significant dead code removal, cleanup, and roughly 250 issues found and fixed during hardening.
- All historical data from Langfuse was lost in the cutover; the system is rebuilding data going forward.
- Improvements from the new stack include faster scoring and lower token consumption.
- There were integration problems with Better Stack and some latency issues during the transition, but these were resolved.

### 2. Internal Agent Ingestion (Better Stack / Trace Data)
- Andrew and Lior debugged why an internal service (Tricentis AI Usage Service) wasn't showing traces. Root cause: spans being ingested did not contain actual agent data (messages, tool calls), so they were being correctly dropped as noise.
- Lior noted that "service" in TAIS does not map one-to-one to an agent in Better Stack. A single session can span multiple services, and only whichever service emits the span with an agent name gets attributed.
- Conclusion: ingesting internal agents in their current state provides close to no value, since there's no standardization across products on how agent spans are emitted. Real signal will come from external customer traces instead.

### 3. Scorecard / Traffic Light Mechanism
- Same underlying mechanism as before (verdict bands), traffic light is just a new presentation layer on top.
- Core limitation: the system currently scores traces, not sessions, and doesn't have a reliable way to detect session boundaries (start/end).
- Discussion of how to define a session boundary across use cases: interactive chat sessions (clear start/new-session action) vs. autonomous/background agents (e.g., a CI/CD pipeline triggered by a commit) where there's no natural "new session" signal.
- Lior framed two product-level approaches:
  - **Proactive/on-demand testing:** user explicitly starts and ends a session for scoring (debugging-style use).
  - **Continuous monitoring:** system scores continuously without user-defined boundaries, but this raises cost/token-consumption questions the team hasn't resolved.
- Technical options discussed for detecting session boundaries: use an existing session ID and aggregate traces by it; infer session end via inactivity/timeout; provide a CLI/SDK call to explicitly start and end sessions; group by time window. No single option was chosen.

### 4. Dynamic Scoring Profiles
- Current system has about 9 fixed scoring profiles; the team manually pulls traces via Claude Code to figure out which profile fits and hardcodes new ones as needed. This does not scale.
- Users need the ability to define what they care about (e.g., correctness weighted at 40%, safety weighted differently) rather than being forced into a fixed profile.
- There is also no "correction" mechanism today, so users have no way to act on a score to improve their agent.
- Lior and Andrew agreed this and session-boundary detection are the two highest-priority product gaps.

### 5. TAIS Integration
- Andrew asked what the team gets out of finishing TAIS integration now. Lior's view: mostly near-term operational overhead ("headache"), with real payoff only once the team is ready to bill clients through TAIS.
- Preparation work Lior wants to start now: consolidating to a single database plus S3 (done), and researching a move from a self-run Postgres container to RDS, since TAIS will run on RDS. Lior wants this migration done early to avoid surprises later.
- One open blocker: no decision yet from Michelle on the identity approach for TAIS.
- TAIS integration has two sub-tracks: operational (billing, deployment) and feature-level (commercialization, AI Hub, identity, platform scale). Not urgent yet since early external beta testing will use a custom one-off setup rather than the full TAIS stack.

### 6. LLM-as-Judge and Internal Agent Onboarding
- Internal ML engineers (including someone on the ATA/ATP agent team) want to run their own agents through AgentScore and compare results against evals they've already run independently.
- Key risk flagged by Lior: if the internal team's own evals used a different judge model (e.g., GPT-something) than AgentScore's current default (Sonnet 5), the scores won't be comparable.
- The backend already supports configuring which LLM is used as judge, but there's no way for a user to select it yet. Lior will need to add that as a user-facing option.
- Follow-up question raised: should end clients be able to see or change which LLM is used as judge? Andrew's take: probably needs RBAC eventually (admin can configure judge model, standard users can view/score but not change it).
- Related question: how judge model choice interacts with future AI credit billing/pricing, since running Opus as judge shouldn't cost the same as Sonnet. Andrew noted this may piggyback on however AI Workspace resolves bring-your-own-LLM billing, which is still being worked out.

### 7. Persistence Layer / RDS Testing
- The teammate handling the Postgres/S3 persistence layer confirmed it is functionally complete: black-box testing with QA is done, only local manual testing remains, and it's safe to move forward.
- Lior asked this same teammate to prioritize RDS compatibility testing next, specifically to catch any Postgres-specific features in use that aren't supported on RDS, before the team is forced to deal with it under time pressure closer to the TAIS cutover.
- Current environment: Postgres running locally in Docker, S3 emulated via local MinIO. Next step is testing against real RDS and real S3.
- Team agreed to close out the current migration epic (it's done) and open a new epic for the RDS/environment-parity work.

## Decisions Made
- Session-based scoring and dynamic scoring profiles are the two highest-priority product improvements to pursue next.
- The current internal-agent-only ingestion effort provides little value and should not be a priority; external customer traces are the better path for feedback.
- Move the persistence layer from local Postgres/MinIO to real RDS/S3 as a priority preparation step for TAIS, ahead of the identity and commercialization work.
- Close out the current Langfuse migration epic; open a new epic for RDS/environment-parity work.
- Internal agent teams testing AgentScore should use the same LLM judge they used for their own independent evals, to keep comparisons apples-to-apples until judge selection is user-configurable.
