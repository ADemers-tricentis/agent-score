# AgentScore Standup — Meeting Summary (Sept 8)

_Technical details, explained for a PM._

## The big topic: TAIS migration, phased

### Where the code actually is today

Lior clarified a point of confusion up front: AgentScore lives in one repo, but it's **not** one deployable blob. It's already decomposed into separate services running in AWS today - frontend, backend, ingest workers, and platform - each its own container with its own Helm chart and its own scaling knobs. Andrew confirmed his understanding: it stays a monorepo, just with separate deployment targets. Migrating to TAIS is porting that existing decomposition onto new infrastructure, not doing the decomposition work itself.

### The three-phase plan

Lior laid out the sequence:

- **Phase 1:** deploy the three existing services (customer app, back office, platform) into TAIS, backed by RDS and S3, configured the same way they are in AWS today. No new capability - just a lift onto the new infra.
- **Phase 2:** identity integration.
- **Phase 3:** AI Hub integration and other features that depend on identity being in place.

Identity has to come second, not third or in parallel, because AI Hub and commercialization both depend on it.

### Sohil's infra work and one open risk

Sohil is deploying the infrastructure pieces (RDS, S3) and reported the permissions issue that had been blocking him is now cleared by the infra team. He flagged a real concern: read and write paths currently sit on the same pod, which means a spike in traffic on one could take down the other - a user-facing outage risk, not just a performance one. Lior's advice: deploy AgentScore locally first (ingest, platform, walkers, MinIO, Postgres) to directly verify whether read/write are actually decoupled before attempting the TAIS deployment. Sohil has run this locally but still needs to confirm the decoupling holds - both paths currently go down together when one fails, which is the thing to chase down before it becomes a production incident.

Lior will share the architecture docs and the repo's one-click `setup-environment` script so the rest of the team can reproduce this locally too.

## What to watch as PM

1. **Read/write coupling is still unverified.** Sohil's local test showed both paths going down together on failure - that's the outage risk Sohil flagged, not yet closed. Needs confirmation before TAIS deployment, not after.
2. **No single tracking surface for the migration yet.** Work spans RDS, S3, identity integration, and AI Hub integration across multiple people, but nothing consolidates it into one plan - easy for a piece to get dropped. Action item below addresses this.
3. **Internal staging usage gap, raised by Andrew.** Internal testers currently can't meaningfully test the system: they either hit the AI Workspace tenant on the EUS production environment (can't manipulate traces there) or they're external users with no access to production data at all. Some staging traces exist for a few agents (ATA, APT, ATC per Michele), but nobody's using staging as part of their actual workflow, so there's no real signal on whether that data is even useful. This is a product gap independent of the TAIS migration - internal users effectively have nowhere to test against today.
