Part 2 has no equivalent source doc - the beta tracker names "onboarding flow" and "feedback channel" as Section 2 deliverables but never defines what to measure, so it's specified here.

## Part 1: Commercial / Cost Metrics

### Why these metrics

The commercial model doc locks two decisions this list has to serve:

- **Scoring run is the value metric, and is now also the sole billing unit** - not trace volume, not seats, and (per the latest decision) not LLM-call count or model tier either. Ingestion stays bundled/free by design. We may use a `credits = f(#LLM calls in the run, model tier)` formula floated in `docs/research/billing-model-research.md` - this will cause more complicated agents and more sophisticated models to cost the user more.
- **Credits-equivalent consumption is tracked but not billed** during the beta, to calibrate the eventual price. With the formula now anchored to run count rather than call/token volume, the open question narrows to *how* a run converts to credits (flat rate per run, or weighted by mode/dimension count) - not *whether* calls or model tier factor in, since they don't.

Token/LLM-call attribution at the **eval/dimension level** (per your earlier answer) is still worth collecting, but its purpose shifts: it's no longer an input to the customer-facing credit formula, since that formula only counts runs. It remains valuable for internal cost/margin visibility - i.e., knowing what a run actually costs Tricentis to serve (which judges ran, per-judge model tier) even though the customer is charged the same per-run regardless.

**Gainsight framing for Part 1:** none of these have a browser-side signal - they're pure backend computations (LLM calls, tokens, credits). Gainsight PX can still be the reporting destination for all of them: the backend computes the value, then pushes it into Gainsight as either a **Track Event** (for per-run granularity, e.g. one event per scoring run carrying judge/token/model attributes) or a **Company-level Custom Attribute** (for a rolled-up per-tenant-per-period number, e.g. credits consumed this week). Gainsight's account model maps `tenant_id` → Gainsight "Company," so every push below joins on that.

## Part 2: Customer Behavior Metrics

### Why these metrics

Part 1 answers "what does a customer cost us." This part answers the question the beta actually exists to answer: **are users getting value out of this, fast enough that they'd be upset if we took it away?** Cost metrics can't tell us that - a tenant can generate scoring runs on schedule without a single human ever looking at the results. These metrics are about human behavior in the product: did they get set up, did they come back, what did they actually use, and where did they give up.

**Revised approach: Gainsight PX as the single destination, both for what it captures natively and for backend state pushed into it.**

- **Native PX capture (little to no custom event code, most of it configured in Gainsight's admin console once the SDK + `identify()` call are in):** page views, click/element-based funnels, time-on-page, and session-based retention/adoption reporting (DAU/WAU, stickiness) are all things PX's Visual Design Studio tags without a code change per metric. This covers #14 (page/section visits), #15 (dialog funnel completion), #17 (docs engagement/dwell time), and #18 (retention) almost entirely through configuration.
- **PX's onboarding/engagement module** (Guides, Checklists, "Engagements") is purpose-built for #13 (checklist/tour engagement) and can also drive #12 (time-to-first-value milestones) if the checklist itself is authored in PX rather than custom-built in our frontend - worth deciding explicitly since that's a UX-ownership question, not just an instrumentation one (see Open Questions).
- **Backend state changes pushed as Track Events**, since a click doesn't guarantee the backend call succeeded: #10 (agent creation), #16 (profile-fit override), #19 (API key setup), and the milestone events in #12 that are backend-side (first trace ingested, first scoring run completed) are pushed from the backend into Gainsight rather than inferred from the client.

Because the code-minimization constraint is dropped, there's no more "backend log vs. client tool" split - everything routes to Gainsight, either via its SDK (client behavior) or its Track Event / Custom Attribute API (backend state).

**Before wiring in Gainsight for named-user behavioral tracking:** the beta tracker's Legal & Compliance section already gates on a PII/DPA review for trace data and a beta clickthrough/consent framework (Christopher LaPoint / Christopher Colosimo). Behavioral tracking of named users should go through the same review, and the beta consent flow should probably disclose it - flagged in Open Questions below. This applies regardless of tool choice, but is worth re-confirming for Gainsight specifically since it's an existing Tricentis vendor relationship, which may or may not already cover this use case's DPA scope.

## Rollup and join keys

Gainsight's own object model replaces the custom rollup tables the first draft assumed: `tenant_id` maps to a Gainsight **Company**, `user_id` maps to a Gainsight **User** (Person) scoped to that Company. Every Track Event and Custom Attribute above should carry both wherever both are meaningful - Part 1's cost metrics are Company-level only, Part 2's behavior metrics need the User join to tell "one admin doing everything" apart from "the whole team is engaged." Gainsight's dashboards roll these up to whatever period you configure (week, to match the "weekly usage dashboard" ask), while the underlying Track Events stay queryable at `run_id` / `user_id` / action grain for drill-down - no separate per-tenant-per-period table needs to be built and maintained on our side.
