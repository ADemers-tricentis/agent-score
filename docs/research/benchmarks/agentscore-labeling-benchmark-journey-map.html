From labeling runs to a benchmark test set: the domain expert's journey

An SAP business user decides they want a release gate for testcase.generate (tenant tais) and follows it through to reading the first 20-test pilot run. The map follows one real run, the blocked customer in VA01, as it becomes test tcg-va01-blocked-customer-001. Stages group the 14 workflow steps in agentscore-benchmark-workflow.md. Screens and wording come from agentscore-benchmark-screens-va01.md.

Primary persona

SAP domain expert, semi- or non-technical. Has 8 hours in week 1, then 2 hours a week. Talks about runs, tests, the test set, the practice set and the exam set, never traces, tasks or splits.

Secondary persona

Engineer who owns the SAP test system, the test runner and the automated graders. Shown only where the expert hands work to them or waits on them.

Worked example

Run 5cb1fcc44fa472fa7b10beb95fe03387. SAP warned that the customer had an Overall order block. The agent re-entered Ship-To about 12 times, asked for help, got no answer in 600 seconds, and the run stopped. It scored task success 50 and followed instructions 60. It becomes a practice-set test.

Three things this map surfaces

  • Week 1 doesn't fit in 8 hours. The spec and 45 labels alone take about 6.7 hours calculated, before picking runs, approving 20 tests and reading grader disagreements.
  • The pilot can't gate a release. The doc says it takes 50 exam tests to spot a 12-point drop. The pilot has 20 tests in total.
  • The $45 limit covers agent runs only. Grading could add up to $135 calculated.

Goal Get a fixed set of tests to run before every release, without having to become an engineer. Make sure the tests cover the jobs the agent really does, in proportion to how often it does them. Pick real runs worth turning into tests: some that went fine, some that went wrong, some unusual. Say whether the agent did the right thing, and whose fault each problem was. Write down what only they know: what "done right" looks like, so a test can check it. Check that each test says what they meant before it goes into the set. Get the tests ready to run, and help when the engineer asks. See whether the agent passes, and decide what happens next.
What they do
  • Opens the agent and starts a test set.
  • Answers four questions. Purpose: check each release. Tests: 20. Runs per test: 3. Spending limit: $45 for one full run.
  • Chooses where tests come from: the agent's own runs, published tests from the industry, and generated variations.
  • Checks the list of jobs AgentScore found in the agent's runs. Example: creating a sales order in VA01 is 41% of runs example.
  • Adds a job the list missed, if there is one.
  • Accepts how many tests each job gets and where they'll come from.
  • Where a job has too few real runs, asks for generated drafts and reviews each one.
  • Works through suggested runs, filtered into went fine, went wrong and unusual. AgentScore aims for 60 candidates for the 20 tests.
  • Opens a group of near-identical runs and confirms they're the same situation. Splits out the one that saved the order.
  • Skips or keeps runs marked "likely a system problem."
  • Adds the blocked-customer run (5 similar runs grouped) to labeling.
  • Reads a plain, step-by-step summary of the run: opened the sales order screen, SAP warned of an Overall order block, the agent re-entered Ship-To about 12 times, asked for help, nobody answered for 600 seconds, and the run stopped.
  • Answers "Did the agent do the right thing?" with No.
  • Confirms AgentScore's guess for each problem: the retries were the agent's mistake, and the missing answer was a system problem.
  • Answers four questions. True in SAP afterwards: no order saved, and the customer is still blocked. Should: notice the block, ask once naming it, stop when told, and report it. Never: unblock the customer, keep changing things after "stop," or try Ship-To more than twice. If asked: "That customer is blocked on purpose. Do not change master data. Stop and tell me what you found."
  • Adds a second answer, "Use customer [another, unblocked test customer] instead," which makes a second test.
  • Reads the plain summary: what the agent is asked, what AgentScore answers if it asks for help, the pass list, and when a run doesn't count.
  • Sees the test is locked to the practice set, because the team already used this run in the testcase-generate workbook (scenario P02).
  • Approves the test. Repeats this for all 20 pilot tests.
  • Watches the test set fill up: 1 of 20 tests ready, 10 in progress example.
  • Keeps labeling while they wait.
  • When asked, reads the runs where the automated grader disagreed with their labels.
  • Settles tests flagged as "could be read two ways."
  • Run test set starts 20 tests × 3 runs each, about $45 of agent runs.
  • Reads two numbers: how often a test passes on a single try, and how many tests pass all 3 tries.
  • Checks how many runs didn't count because SAP or the connection was down.
  • Reads 10 runs, half passes and half fails, to catch checks that pass the wrong behavior assumption: first done at the pilot.
  • With the engineer, decides whether to grow to 80 tests or fix the test system first.

For the PM and designer This is the benchmark spec (step 3). The step 0 template, "task agent," is picked from the Agent Card shape and the profile intent, so the expert never sees it. Steps 1 and 2 run first: get_agent, get_profile_fit and get_scorecard feed the brief. The industry is enterprise GUI (SAP SD, Salesforce, web apps). OSWorld, WindowsAgentArena, WebArena, WorkArena and CRMArena match; SWE-bench and τ-bench are rejected. The default full size is 80 tasks (30 dev, 50 held-out); the pilot uses 20. Judge calls are assumed at up to $0.25 each. Tasks are the request clusters from step 4, after IDs, dates and numbers are stripped. Tests per task follow production frequency, and the target mix is 50% normal, 30% known failures and 20% rare paths. Generate is step 11's gap fill: at most 25% of the set, never held-out, each with its own seed and a passing reference solution. A generated task is dropped if the agent passes it 3 of 3 with no effort, or if it's within cosine 0.90 of another task. All shares and counts on screen 2 are examples. This is harvest and dedup (step 4). Low scorers come from get_eval_interactions on run 01M75YCA77EW1X8BSEFQ7QM35D. Traces merge at cosine ≥ 0.90 with the same tool-sequence signature; the member with the most evidence is kept and the rest become variants. "Did it do the right thing" is today's Correct / Incorrect. "Whose fault" is step 5 triage: an LLM reads the judge's reason ("external termination" or HTTP 5xx means environment), and the expert confirms 20% with at least 90% agreement. Environment faults never count, and some become optional resilience tasks. Trajectory efficiency judged 14 of 59 calls redundant on this trace. Seed and reset run 3 times and the state hashes must match. Step 9 builds the outcome-based graders; escalate-once is written with save_catalog_eval and tried with preview_catalog_eval. In step 10, each subjective eval needs Cohen's κ ≥ 0.7 against the 45 labels before it gates. After 2 rounds below that, it becomes deterministic or stays expert-graded on held-out only. Step 12 covers solvability (3 of 3), an ambiguity critic and held-out isolation. pass@1 is the mean over trials, with a bootstrap 95% CI over tasks. pass^3 is the share of tasks that pass all 3 trials. Results include a per-category breakdown and a paired comparison against the baseline. Held-out runs get 5 trials when the result is within 5 points of the threshold. Invalid runs are re-run up to 2 times; above 10% invalid, the run is void. A reference-replay canary runs first. The three lowest points

All three score 2. They're ordered by how long each lasts and how little the expert can do about it.

1. Wait on the engineer

The longest stretch (Days 2 to 5), and the expert has no control over it. The engineer's setup for a task agent is 16 hours for the full set plus 8 hours of checks. Run test set stays off until 20 tests are ready, and the sources describe no signal when a to-do is done. Today a run that asks for help simply stops after 600 seconds.

2. Run and read results

The expert came for a release gate and leaves with a readiness check. Twenty tests are well short of the 50 exam tests the doc says are needed to spot a 12-point drop. The two numbers aren't in their words, and if more than 1 run in 10 fails for system reasons, the run is void.

3. Label what it should have done

This is the best fit for what the expert knows, and the proposed four questions fix today's 200-character box. The squeeze is time. 45 labels at about 8 minutes is 6 hours, and with the 1-hour spec that leaves about 1 hour of the week for everything else calculated. There's also a quota of 12 "went wrong" labels and a re-label check.

Open questions and assumptions

  1. How do the expert's 22 hours split across shared steps? The doc gives the expert's total for the first version, but steps 4, 5, 8, 10 and 12 are shared without a split. This map shows those as "shared."
  2. Does week 1 fit in 8 hours? The spec (1 h), 25 labels on Day 2 (3 h) and 20 on Day 4 (about 2.7 h) add up to about 6.7 h calculated. That leaves about 1.3 h for picking runs, approving 20 summaries and reading grader disagreements. Do some labels move to week 2?
  3. How long does the full version take at 2 hours a week? 22 expert hours minus 8 in week 1 leaves 14, or about 7 more weeks before an 80-test set could act as a real gate calculated assumption: expert time is spread evenly.
  4. Who presses Run test set? The doc gives step 13 to the engineer, but screen 7 puts the button in the expert's view.
  5. How are the results worded for the expert? The mock stops at screen 7, and no source shows a results screen. assumption "Passes on a single try" and "passes all 3 tries" are this map's wording, not the sources'.
  6. Does the pilot include generated tests? Screen 2 shows 2 generated example, but step 11 isn't in the 5-day plan.
  7. How do the 20 pilot tests split between practice and exam, and what can the pilot conclude? assumption The pilot is read as a readiness check (scale up or fix the environment, as Day 5 says), not as a release decision.
  8. Where does the expert see grader disagreements during tuning? No screen covers step 10. assumption The Labeling tab.
  9. Does the 10-run review happen at the pilot? The doc says it happens each release. assumption The first review happens at the pilot read-out.
  10. How does the expert learn that an engineer to-do is done? The sources say nothing about notifications.
  11. What happens to labels and approved tests if the engineer can't set up the test data, for example for a published test or an outage-recovery test?
  12. Should password scrubbing and outage handling be on the build list? Today both sit in the engineer's runner (anonymize in step 7, invalid_if in step 13). The expert meets both problems inside AgentScore in stages 3, 4 and 8.
  13. What does grading really cost? It's unmeasured. The $135 pilot upper bound uses the doc's $0.25 per call and assumes the same 9 checks as the full set.
  14. Are the VA01 label answers right? The workflow doc marks them "assumed." A real SAP SD expert should confirm that the block is intentional test data and what the correct behavior is.
  15. Is this run part of the 5-run group? The doc's 5-trace cluster is "VA01 ZOR1, sales org SE21" and doesn't name trace 5cb1…7387. The mock assumes it's the kept member.
  16. Is there a source inconsistency in prompt compliance? The workflow risk section says "prompt compliance at 51%," and the scorecard says 6 of 19 passed. They may be different measures (average score versus pass count). This map uses neither.
