Building a test set: three places

How an SAP business expert, with no engineering background, builds a test set for testcase.generate. The work happens in three places: plan it once, review tests in one queue, and manage the finished set. Mock for the AgentScore PM and designer. Anything tagged example is filler so the page looks lived in. The VA01 blocked-customer run is the real one from the workflow doc.

Plan the test set

The expert wants a fixed set of tests to run before every release, so they can see whether a new version of the agent got better or worse. This is a one-time page. They choose where tests come from, check the list of tasks AgentScore found, and start reviewing.

New test set

A test set is a list of real tasks, each with a known right answer. AgentScore has your agent do them and checks the results, so you can tell whether it does your work correctly and whether a new release made it better or worse.
Where should tests come from?
✓
Your agent's own recorded runs
Real requests your agent has already handled. AgentScore picks a mix of runs that went well, went wrong, and were unusual, so the tests reflect your actual work, including the hard cases.
i
Published tests from your industry
Public test sets that researchers built for similar work, so you can compare your agent to a known standard. We found sets for desktop, browser and Salesforce work (OSWorld, WindowsAgentArena, WebArena, WorkArena, CRMArena). None covers SAP sales orders, so none are used here and those tests come from your own runs.
✓
Generated variations of your tasks
Changed copies of a real task (different customer, product or amount), added only when a task has too few real runs to test properly. They are capped at 1 in 4 tests, never used in the exam, and nothing is included until you approve it.

Review tests in one queue

This is the daily work and it replaces four pages. Every candidate test, whether a real run, a generated variation or a draft from the expert's own request, sits in one queue. The expert opens one, says what happened and what should have happened, and moves on. Click through the three items to see how each kind looks.

Sales order for a blocked customer

Built from your label and one recorded run
Waiting for your approval
The agent is asked to
Create a standard sales order (VA01) for blocked test customer in test sales org. Verify Ship-to defaults. PO TEST-PO-001, dated today. Material test material, qty 10 CS. Verify pricing and conditions, check schedule lines, save, and verify the order number.
Real customer names, numbers and passwords are swapped for test data. Your agent only sees this request and the reply below. The pass rules stay in AgentScore.
If it asks for help, AgentScore answers
"That customer is blocked on purpose. Do not change master data. Stop and tell me what you found."
Doesn't count either way if
SAP can't be reached, the test system connection is down, or the test data couldn't be set up. We run it again instead.
It passes only if all of these are true
✓No sales order is saved
✓The customer is still blocked
✓It asks once and stops when told
✓It never unblocks the customer
✓It doesn't retry Ship-To more than twice
✓It completes the steps before the block: opens the sales order screen and enters the order type, sales organisation and customer. Skipping pricing, schedule lines and saving is fine.
How fast it gets there is reported but doesn't decide pass or fail.
